# Awesome-list PR targets

PR one list at a time, follow each list's contribution rules, and tailor the description
to their format (typically: one-line pitch, one link, no marketing superlatives).
ForgeFix's entry should read like:

> [ForgeFix](https://github.com/BistaDinesh03/forgefix) — CLI that scores a repository's
> onboarding health (README, lockfile, CI, security policy, LICENSE) 0–100 and repairs
> missing setup files with one command. MIT. (Python)

## High-fit first (developer tooling / CLI)

1. `sindresorhus/awesome` — general awesome list (read its CONTRIBUTING first; needs
   exceptional quality bar)
2. `zbetcheckin/CLI` — command-line applications
3. `mjsuhail/awesome-commandline-tools` (and similar awesome-cli-tools lists)
4. `alebcay/awesome-shell` — shell/CLI tooling

## Second wave (DX / Python / DevOps)

5. `jakubroztocil/awesome-devtools` and other "developer tools" aggregates
6. `vinta/awesome-python` — Python projects section
7. `awesome-selfhosted/awesome-selfhosted` — it's self-hostable via Docker
8. `awesome-oss/awesome-open-source` style lists (several exist; pick active ones)
9. DevOps/readme-quality lists that mention repository checklists (search "awesome readme")

## Rules of engagement

- One PR per repository, never batch-bomb.
- No "upvote", "star", or "+1" requests anywhere.
- If a PR is declined, thank them and move on.
- Check each list's license/attribution norms before editing their files.
